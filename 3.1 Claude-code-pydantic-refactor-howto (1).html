Running a Pydantic-Adoption Refactor with Claude Code

A concrete, safety-first walkthrough that uses Claude Code's real configuration surfaces — CLAUDE.md, path-scoped rules, hooks, and custom skills (slash commands) — organized around the four phases Anthropic's own Claude Code in Action course teaches: Steer, Configure, Automate, and Verify & Share.

On the course reference: anthropic.skilljar.com/claude-code-in-action is Anthropic's official course, "Claude Code in Action." Its lesson content sits behind a Skilljar login, so this guide doesn't quote from inside it — only the publicly listed course description and curriculum were available: Steer the Work (plan mode, compaction, the rewind menu, goal/loop runs), Configure Claude (a lean CLAUDE.md, skills, permission modes, hooks), Automate Repeat Work (routines, headless mode, GitHub Actions and code review), and Verify and Share (verifying unsupervised runs, gating on real test results, packaging a plugin). This guide is organized to mirror that shape and applies it concretely to one task — Pydantic adoption — using the documented mechanics of each feature at docs.claude.com. If you have course access, the "A CLAUDE.md That Follows," "Hooks," and "Trust It: Verifying Unsupervised Runs" lessons will go deeper than what's here.
Scope note: "Custom commands" in Claude Code are implemented as skills (a SKILL.md file under .claude/skills/<name>/). The older .claude/commands/*.md format still works but skills are recommended and used throughout.

0. Before you start: set up a safety net

These aren't Claude Code features — they're the ordinary engineering safety net a refactor needs regardless of tooling.

  • Work on a dedicated branch: git checkout -b refactor/pydantic-adoption
  • Confirm the test suite passes before Claude touches anything, so you have a real baseline: pytest -q
  • Commit or stash any unrelated in-flight work. Claude Code's checkpoint/rewind feature (/rewind) automatically snapshots code before every prompt in the session and lets you revert, but it only tracks edits made through Claude's own Edit/Write tools — not Bash-driven changes (rm, mv), not most subagent/background work, and not symlinked files. Treat it as fast in-session undo, not a substitute for git history.

Phase 1 — Steer
1. Give Claude persistent project context — CLAUDE.md

CLAUDE.md is loaded into every session and is the right place for durable facts: build/test commands and the project's Pydantic conventions. Run /init first if you don't have one — it generates a starting file from your codebase. Keep it under ~200 lines; anything longer reduces how reliably Claude follows it.

./CLAUDE.md 
# Project: <your project name>

## Build & test
- Install: `pip install -e ".[dev]"`
- Run tests: `pytest -q`
- Lint: `ruff check .`
- Type check: `mypy src/`

## Pydantic conventions (target state for this refactor)
- Standardize on **Pydantic v2** for all data crossing module or API boundaries.
- New/migrated models subclass `pydantic.BaseModel`.
- Use `field_validator` / `model_validator`, not v1's `@validator`.
- Configure models with `model_config = ConfigDict(...)`, not an inner `class Config`.
- Serialize with `.model_dump()` / `.model_dump_json()`, not `.dict()` / `.json()`.
- Settings load via `pydantic-settings.BaseSettings`, not raw `os.environ` reads.
- Don't introduce new `@dataclass` or `TypedDict` types for data that crosses a
  module or API boundary — use a Pydantic model instead. Dataclasses remain fine
  for small, purely internal value objects that never leave a function.

## Refactor session rules
- Never edit database migration files or lockfiles as part of this refactor.
- One logical change per commit (e.g. "migrate UserPayload to Pydantic v2").
- Run the affected tests after every file change, not just at the end.
Run /context in a session afterward and confirm CLAUDE.md appears under Memory files — if it's missing there, Claude never saw it.

2. Scope detailed conventions with a path-specific rule

Full v1→v2 migration detail doesn't need to sit in context for every session — only when Claude is actually touching Python files. A rule in .claude/rules/ with a paths filter loads on demand instead of every session, keeping CLAUDE.md lean.

.claude/rules/pydantic.md 
---
paths:
  - "src/**/*.py"
  - "tests/**/*.py"
---

# Pydantic v2 migration rules

- Prefer `field_validator(mode="before"|"after")` over v1's `@validator`.
- Prefer `model_validator(mode="before"|"after")` over v1's `@root_validator`.
- Replace `class Config:` blocks with `model_config = ConfigDict(...)`.
- Replace `.dict()` → `.model_dump()`, `.json()` → `.model_dump_json()`.
- When a field was previously untyped or loosely typed, add the narrowest
  correct type — but don't add new validation constraints (min_length, regex,
  etc.) unless the audit specifically flagged missing validation. Speculative
  constraints can break existing valid data.
- Preserve default values and Optional-ness exactly as they were before
  migration. A behavior change is a bug in this refactor, not a bonus fix.
- If a dataclass or TypedDict is purely internal (never serialized, never
  crosses a function boundary into another module), leave it alone.

Phase 2 — Configure
3. Add safety hooks

CLAUDE.md and rules are context — Claude tries to follow them but nothing enforces it. Hooks are shell commands Claude Code runs deterministically at fixed lifecycle points, regardless of what the model decides. Use them for the two things you actually want guaranteed: migrations/lockfiles never get touched, and Claude can't claim to be done while tests are failing.

3a. Block edits to migrations and lockfiles

.claude/hooks/protect-migration-files.sh 
#!/bin/bash
# Blocks Edit/Write on migration and lockfile paths during the refactor.
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
FILE_PATH="${FILE_PATH//\\//}"   # normalize Windows separators

PROTECTED_PATTERNS=(
  "alembic/versions/"
  "/migrations/"
  "poetry.lock"
  "requirements.txt"
  "requirements-lock.txt"
  "uv.lock"
)

for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH matches protected pattern '$pattern'. This refactor does not touch migrations or lockfiles." >&2
    exit 2
  fi
done

exit 0

Make it executable, then register it as a PreToolUse hook scoped to project settings so it's committed and shared with the team:

.claude/settings.json 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-migration-files.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | grep '\\.py$' | xargs -r ruff check --fix"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify-tests-before-stop.sh"
          }
        ]
      }
    ]
  }
}

chmod +x .claude/hooks/protect-migration-files.sh
chmod +x .claude/hooks/verify-tests-before-stop.sh

3b. Auto-lint every edited file (PostToolUse)

The PostToolUse entry above runs ruff check --fix on any Python file Claude just edited or wrote — instant, deterministic style/import cleanup after every change, with no LLM round-trip.

3c. Don't let Claude declare victory on a red test suite (Stop)

.claude/hooks/verify-tests-before-stop.sh 
#!/bin/bash
# Runs the test suite before Claude is allowed to end its turn.
# Blocks (exit 2) and feeds the failure back to Claude if tests are red.
INPUT=$(cat)

# Avoid an infinite loop: if this hook already blocked once for this stop
# and Claude is stopping again right after, let it through this time.
if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then
  exit 0
fi

if ! pytest -q > /tmp/pydantic-refactor-pytest.log 2>&1; then
  echo "Tests are failing — fix them before stopping. Last 40 lines:" >&2
  tail -n 40 /tmp/pydantic-refactor-pytest.log >&2
  exit 2
fi

exit 0
Why this matters: without the Stop hook, nothing stops Claude from saying "migration complete" while a test is silently broken. With it, Claude Code re-runs the suite every time Claude tries to finish and forces a fix-or-explain loop. If your suite is slow, scope the hook to just the affected test paths, or run it only on PostToolUse for files under src/ instead of on every Stop.

Confirm both hooks registered correctly by typing /hooks in a session — you should see PreToolUse, PostToolUse, and Stop each listed with a count.

4. Create two custom skills (slash commands)

Skills package a repeatable prompt as a /name command. Both skills below set disable-model-invocation: true so Claude can never trigger them on its own — you decide when the audit runs and when the refactor executes.

4a. /pydantic-audit — read-only diagnostic

.claude/skills/pydantic-audit/SKILL.md 
---
name: pydantic-audit
description: Audit this codebase's Pydantic adoption (version, usage patterns, competing data types) and report findings. Read-only — makes no edits.
disable-model-invocation: true
allowed-tools: Bash(pip show pydantic) Bash(rg *) Bash(grep -rn *) Read Grep Glob
---

Audit this codebase's Pydantic adoption. **Do not edit any files during this
skill** — this is a read-only diagnostic pass.

1. Find the installed Pydantic version: `pip show pydantic`
2. Find all Pydantic model definitions (search for `BaseModel`)
3. Find v1-style patterns needing migration: `.dict()`, `.json()`,
   `@validator`, `@root_validator`, an inner `class Config`
4. Find competing patterns used for data that crosses a module or API
   boundary: `@dataclass`, `TypedDict`, raw `dict`
5. Check whether settings load via `pydantic-settings` or raw `os.environ`
6. If SQLAlchemy is present, check for unnecessary duplication between ORM
   models and Pydantic models, and whether `from_attributes`/`orm_mode`
   bridges them

Report the findings as a table: file path, current pattern, recommended
target pattern, priority (high/medium/low), and a one-line reason. End with a
short summary paragraph. Do not propose a step-by-step refactor plan yet —
that's a separate step, after I've reviewed this audit.

4b. /pydantic-refactor — execute an approved plan

.claude/skills/pydantic-refactor/SKILL.md 
---
name: pydantic-refactor
description: Execute an approved Pydantic-v2 migration for the given file or module, following CLAUDE.md and .claude/rules/pydantic.md.
disable-model-invocation: true
argument-hint: [path]
---

Refactor $ARGUMENTS to standardize on Pydantic v2, following the conventions
in CLAUDE.md and `.claude/rules/pydantic.md`.

1. Re-read the target file(s) first and confirm the plan still applies —
   code may have changed since the audit was written.
2. Convert dataclasses, TypedDicts, or raw dicts that cross a module or API
   boundary into Pydantic v2 `BaseModel` classes.
3. Migrate v1-style syntax: `@validator` → `field_validator`,
   `@root_validator` → `model_validator`, `class Config` → `model_config`,
   `.dict()`/`.json()` → `.model_dump()`/`.model_dump_json()`.
4. Preserve existing field defaults, optionality, and runtime behavior
   exactly. Do not add new validation constraints unless the audit flagged
   missing validation for this specific field.
5. Run the tests for the affected module after finishing this file.
6. If a test fails, stop and report it — do not loosen the test or the model
   to make it pass without understanding why.

Work one file at a time. Keep each file's change as its own commit with a
message like "migrate <ModuleName> to Pydantic v2".
Both skills use disable-model-invocation: true, so they never appear as something Claude decides to run on its own — only you can type /pydantic-audit or /pydantic-refactor src/api/users.py.

Phase 1 — Steer
5. Run the session — Plan Mode first

Plan Mode tells Claude to research and propose changes without editing anything. Except in sessions with bypass-permissions enabled, file edits stay blocked until you explicitly approve a plan — this is the "look before you leap" phase.

StepAction
1Start Claude Code in the project root: claude --permission-mode plan (or start normally and press Shift+Tab until the status bar shows ⏸ plan mode on)
2Run the audit: /pydantic-audit
3Review the table Claude produces. Ask follow-up questions or narrow scope in conversation — you're still in plan mode, so nothing gets edited
4Ask Claude to turn the audit into a concrete plan: "Based on this audit, draft a refactor plan: which files to migrate, in what order (lowest-risk first), and how to sequence commits."
5When the plan is ready, press Ctrl+G to open it in your editor and hand-edit it directly if needed
6Approve it. Claude Code offers a choice: "Yes, manually approve edits" (review every diff) or "Yes, auto-accept edits"/"Yes, and use auto mode" (fewer prompts). For a refactor touching many files with unfamiliar risk, start with manual approval
Approving a plan exits Plan Mode and switches you into the mode you selected (manual review or acceptEdits) — Claude then starts editing. You can always cycle back into Plan Mode with Shift+Tab or /plan if you want to re-plan a later phase (e.g. after the low-risk files are done, before tackling the risky ones). If a step goes sideways mid-session, /rewind (or double-Esc) opens the checkpoint menu to revert code, conversation, or both to an earlier prompt — faster than a git revert for in-session mistakes, though it doesn't replace git for anything you want to keep permanently.

6. Direct execution phase

Once the plan is approved, drive the actual migration file-by-file with the second skill rather than one giant instruction — this keeps each unit of work small, reviewable, and bounded by the hooks from Step 3.

/pydantic-refactor src/api/schemas/user_payload.py

For each file:

  • The PreToolUse hook silently blocks any accidental touch to a migration or lockfile
  • The PostToolUse hook auto-runs ruff check --fix after every edit — you'll see no output on success
  • Review the diff with /diff before moving to the next file (or after each batch, if you chose auto-accept)
  • The Stop hook re-runs the full test suite before Claude can finish its turn and will force a fix loop if something regresses

Repeat for each file in the plan's sequence, lowest-risk first. If a file turns out to need more judgment than expected, drop back into Plan Mode (/plan) for that file specifically before resuming execution.

Phase 3 — Automate
7. Run the audit unattended with headless mode

Once the audit skill is stable, you don't need an interactive session to run it — for example, as a periodic drift check that flags new dataclasses/TypedDicts sneaking back into the codebase. Claude Code's -p (--print) flag runs one prompt non-interactively and exits, which is the same mechanism behind CI jobs, cron jobs, and the GitHub Action.

claude -p "/pydantic-audit" \
  --allowedTools "Bash(pip show pydantic),Bash(rg *),Bash(grep -rn *),Read,Grep,Glob" \
  --max-turns 20 \
  --output-format json > pydantic-audit-report.json
FlagWhy it's here
-pNon-interactive: sends the prompt, prints the result, exits. There's no permission prompt loop in headless mode, so tools must be pre-authorized or the run stalls.
--allowedToolsScopes exactly what the audit is allowed to run — mirrors the skill's own allowed-tools frontmatter. Keep this narrow; headless runs have no human in the loop to catch an over-broad grant.
--max-turnsCaps how many tool calls the run can make before giving up — a sane ceiling for an unattended job.
--output-format jsonMachine-readable result, so a script or CI step can parse it (e.g. fail a build if new v1-style patterns appear).
Headless mode is exactly where the guardrails from Phase 2 matter most — nobody is watching the run to catch a mistake in the moment. Keep --allowedTools scoped to read-only commands for the audit; never run /pydantic-refactor unattended with broad tool access unless the Stop hook (Step 3c) and CI's own test gate are both in place to catch a bad result before it merges.

To schedule this as a recurring check without your own cron infrastructure, Claude Code also supports routines — prompts scheduled to run on Anthropic's own infrastructure rather than a machine you maintain. Ask Claude to set one up in a session (/schedule), or configure it from the web UI, pointing it at the same /pydantic-audit skill.

The less closely you watched a given stretch of work — an overnight run, a headless CI job, a long auto-accept batch — the more of this checklist you should actually run rather than skim. A five-minute manual pass isn't a substitute for the test suite and /code-review on work nobody reviewed as it happened.

8a. Gate it in CI with the GitHub Action

For a repo where this refactor recurs (new PRs re-introducing old patterns), wire the audit into pull request checks with Anthropic's official anthropics/claude-code-action, which wraps the same headless -p mechanism inside GitHub Actions. A minimal step:

- name: Pydantic adoption check
  uses: anthropics/claude-code-action@v1
  with:
    prompt: "/pydantic-audit — fail if any new file introduces a dataclass or TypedDict for API-boundary data"
    claude_args: "--allowedTools Read,Grep,Glob,Bash(pip show pydantic)"
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

Combine this with Claude Code's managed /code-review check on the same PR for a second, independent pass over the diff.

8b. Package the setup as a plugin your team can install

Everything from Steps 1–4 — the rules, hooks, and two skills — is standalone .claude/ configuration right now, useful only in this repo. Once it's proven out, converting it into a plugin lets any teammate add the same audit/refactor toolkit to their project with one command instead of copying files by hand.

  1. Create a plugin directory with a manifest: mkdir -p pydantic-toolkit/.claude-plugin and a plugin.json naming it, e.g. {"name": "pydantic-toolkit", "description": "Audit and refactor helpers for Pydantic v2 adoption"}
  2. Move skills/pydantic-audit/ and skills/pydantic-refactor/ into pydantic-toolkit/skills/
  3. Move the hooks into pydantic-toolkit/hooks/hooks.json, copying the same hooks object from .claude/settings.json — the format is identical
  4. Test locally without installing anywhere: claude --plugin-dir ./pydantic-toolkit, then /reload-plugins after any edit
  5. Publish it as a marketplace (a GitHub repo with a .claude-plugin/marketplace.json at the root) so teammates can run /plugin marketplace add your-org/pydantic-toolkit then /plugin install pydantic-toolkit@your-org
Project-specific detail — the actual Pydantic conventions in CLAUDE.md and the paths-scoped rule — stays in each repo's own .claude/. The plugin carries the reusable mechanism (the two skills, the hooks); the target conventions are still something each team states for its own codebase.
