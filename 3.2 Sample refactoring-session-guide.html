Refactoring Session Guide (Template)

A structured walkthrough for running a focused refactoring session on a Python codebase. "Check Pydantic adoption" is one diagnostic step within a broader flow — use the whole template or just the sections you need.

1. Define Scope & Goals

Before touching code, pin down:

  • Target area: one module, one service, or the whole repo?
  • Motivation: performance, readability, type-safety, consistency, preparing for a feature, or paying down tech debt?
  • Definition of done: what does "refactored" mean for this session? (e.g., "all API request/response models use Pydantic", "no bare dicts crossing service boundaries")
  • Non-goals: what you will explicitly not change today (avoids scope creep).

2. Baseline Audit

Get a snapshot of the current state before making changes.

  • Run existing tests and record pass/fail state (refactors should be behavior-preserving; you need a "before" picture).
  • Check test coverage for the target area — low coverage means higher refactor risk.
  • Note current linting/type-checking status (mypy/pyright errors, if any).
  • Identify dependency versions in use (this is where the Pydantic check fits in — see Section 3).

3. Check Pydantic Adoption

Goal: understand how and how consistently Pydantic is used before deciding whether/how to extend or standardize it.

What to look for

CheckWhy it matters
Version in use (pydantic in requirements/lockfile) v1 vs v2 have different APIs (.dict() vs .model_dump(), validator vs field_validator, Config class vs model_config). Mixing versions across services causes subtle bugs.
Where models are defined Are Pydantic models used at API boundaries only (request/response), or also internally for domain logic? Inconsistent boundaries often signal a half-finished migration.
Competing patterns Look for dataclasses, TypedDict, attrs, or raw dict/NamedTuple doing the same job Pydantic models do elsewhere. These are refactor candidates if the goal is consistency.
Validation duplication Manual if checks or custom validators that Pydantic's built-in validation (Field, field_validator, model_validator) could replace.
Serialization patterns Manual json.dumps/asdict calls next to Pydantic's .model_dump_json() — a sign of inconsistent adoption.
Settings management Is pydantic-settings (or v1's BaseSettings) used for config, or is config handled ad hoc via os.environ / dotenv?
ORM/DB layer overlap If using SQLAlchemy or similar, check whether Pydantic models duplicate ORM models unnecessarily, or whether from_attributes/orm_mode is used to bridge them cleanly.

Quick commands to run during the session

(adjust for your tooling)

# Find Pydantic version
pip show pydantic

# Find all Pydantic model definitions
grep -rn "BaseModel" --include="*.py" .

# Find v1-style patterns that may need migration to v2
grep -rn "\.dict()\|\.json()\|@validator\|class Config" --include="*.py" .

# Find competing data patterns worth comparing against Pydantic usage
grep -rn "@dataclass\|TypedDict" --include="*.py" .

Output of this step: a short list — e.g., "12 Pydantic models, all v2-style, but 4 modules still use raw dataclasses for API payloads; settings are handled via os.environ, not pydantic-settings." This becomes input to Section 4.

4. Plan the Refactor

Based on the audit:

  • Decide the target pattern (e.g., "standardize on Pydantic v2 for all data crossing module boundaries").
  • Sequence changes from lowest-risk to highest-risk (pure internal modules before public API contracts).
  • Identify breaking changes (e.g., serialization output format changing) and who/what downstream depends on them.
  • Decide whether this is a big-bang change or an incremental/strangler migration (usually incremental is safer for shared codebases).

5. Execute in Small, Verifiable Steps

  • One logical change per commit (e.g., "migrate UserPayload from dataclass to Pydantic model").
  • Run tests after each step, not just at the end.
  • If migrating Pydantic v1 → v2 syntax, do it as its own isolated pass, separate from behavioral changes.
  • Keep an eye out for silent behavior changes (e.g., Pydantic's default validation/coercion rules differ from manual checks — ints coercing from strings, extra fields being silently dropped vs. rejected).

6. Review & Validate

  • Re-run the full test suite and compare against the Section 2 baseline.
  • Re-run type checking (mypy/pyright) — Pydantic models should improve, not worsen, type coverage.
  • Spot-check serialization output (API responses, logs) for format drift.
  • Peer review focused specifically on: consistency with the target pattern, and any validation behavior changes.

7. Document & Close Out

  • Update any internal docs/README noting "we standardize on Pydantic vX for Y."
  • Note any deliberately deferred items (e.g., "settings module still uses os.environ — tracked as follow-up").
  • Record the session's before/after (test pass rate, lint errors, files touched) for future reference.

Optional: Session Checklist (condensed)

  • Scope and done-criteria defined
  • Baseline tests/lint/type-check recorded
  • Pydantic version + adoption pattern audited
  • Competing data patterns identified
  • Target pattern decided
  • Changes sequenced low → high risk
  • Incremental commits, tests run per step
  • Full validation pass at the end
  • Docs updated, follow-ups tracked
