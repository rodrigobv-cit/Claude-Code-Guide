Claude Code Settings, Explained Simply

Where Claude Code's config files live, who they affect, and which one wins when they disagree.

1Why do settings files even exist?

Claude Code needs to know things like: which AI model to use, what commands it's allowed to run without asking you first, and what files it should never touch. Instead of you re-typing this every single time, you write it down once in a file, and Claude Code reads it automatically.

Think of it like: the settings menu on your phone. Some settings are "just for you" (your wallpaper), some are shared with your family (the Wi-Fi password), and some are locked by your employer if it's a work phone (you can't uninstall the security app). Claude Code has the exact same idea — just spread across a few files instead of one menu.

2The four settings files (plus one you don't touch)

Claude Code checks up to five places for settings. Each one has a different "audience" — who it applies to.

FileLives whereWho it affectsWhat it's for
User settings ~/.claude/settings.json Just you, on this computer, in every project you open Your personal defaults — favorite model, your own permission habits
Shared project settings .claude/settings.json (inside the project folder) Everyone on the team who works in that project Team rules — "everyone can run npm test without asking"
Project local settings .claude/settings.local.json Just you, and only in this one project Your personal exceptions — override the team's file just for yourself
Managed settings Deployed by your company (IT/security) Everyone your company deploys it to Rules nobody can override — e.g. "never run rm -rf"
The fifth file, ~/.claude.json: Claude Code writes this one itself to remember things like your login and MCP server connections. You never need to hand-edit it.
The tilde (~) trick: ~ is shorthand for "your home folder" — like C:\Users\YourName on Windows or /Users/YourName on Mac. So ~/.claude/settings.json means "a hidden folder in MY home directory," separate from any specific project.

3Which file wins when they disagree?

If your personal file says "use model A" and your team's file says "use model B" — who wins? Claude Code always uses the value from the file highest in this list. Higher = more powerful = overrides everything below it.

1
Managed settings — your company's IT policy
managed-settings.json / MDM / claude.ai console
Nothing you do overrides this. Full stop.
↓ overrides everything below
2
Command line — a flag you typed just now
claude --settings '{...}'
Only lasts for this one session — nothing gets saved
↓
3
Project local settings — your personal tweak, this project only
.claude/settings.local.json
You, and only in this one project folder
↓
4
Shared project settings — the team's file
.claude/settings.json
Everyone who clones this repo, once the file is committed
↓
5
User settings — your all-projects defaults
~/.claude/settings.json
You, everywhere, unless something above overrides it
Simple example: Your team's shared file sets the model to Sonnet. You personally prefer Opus. You add "model": "claude-opus-4-8" to YOUR .claude/settings.local.json. Now only your sessions use Opus — your teammates still get Sonnet, because your local file (#3) beats the shared file (#4), but only for you.

4What the folders actually look like

Here's a real layout, side by side — the "your machine, everywhere" folder vs. the "this one project" folder.

Your machine (applies to every project you open)
~/.claude/ ← lives in your home folder ├── settings.json ← your personal defaults └── agents/ ← subagents available in ALL your projects └── code-reviewer.md
Inside one project (only applies there)
my-project/ └── .claude/ ├── settings.json ← committed to git, shared with the team ├── settings.local.json ← yours only — auto-gitignored, never committed ├── CLAUDE.md ← instructions Claude reads every session in this project └── agents/ ← subagents specific to THIS project └── test-runner.md
Why the dot in front? A leading dot (.claude) makes it a "hidden" folder on Mac/Linux — it won't clutter your normal file browser, but it's still there and Claude Code finds it automatically.

5A real settings file, explained line by line

This is what a typical shared team file looks like. Every line does one specific thing.

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Agent"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
LineWhat it means in plain English
$schemaNot a real setting — it just tells your code editor "here's the shape this file should follow" so you get autocomplete and red squiggles if you typo something
permissions.allowA list of things Claude Code can do without asking you first
"Bash(npm run lint)""You're allowed to run exactly this one command, no permission prompt needed"
"Bash(npm run test *)"The * is a wildcard — "any npm run test command, with any extra arguments, is fine"
"Agent""You're allowed to delegate work to subagents" (without this line, Claude can't call any subagent at all)
permissions.denyThe opposite of allow — things Claude is never allowed to do, no matter what
"Read(./.env)""Never let Claude open the .env file" — this is usually where secrets/passwords live, so you keep it off-limits
Watch out: these files are strict JSON — no comments with //, no trailing commas after the last item in a list. One typo and Claude Code will show you an error the next time it starts.

6The one tricky part: lists don't replace, they combine

Most settings work like you'd expect — the higher file wins, end of story. But lists (like permissions.allow) are different: Claude Code adds them all together instead of picking just one.

Example: Your team's shared file allows ["npm test"]. Your personal local file allows ["git push"]. You end up with both — npm test AND git push — not just one or the other. Think of it like two people each adding items to the same shopping list, rather than one person's list replacing the other's.
Practical upshot: if your team already put "Agent" in the shared .claude/settings.json, you don't need to add it again anywhere for yourself — it's already active because the lists get merged, not overwritten.

7How do I know which files are actually being used?

Don't guess — ask Claude Code directly. Run this inside a session:

/status

Look for the line that says "Setting sources" — it lists every settings file Claude Code actually loaded for this session. If a setting you added isn't behaving as expected, this is always the first thing to check.

Edit a settings file → Run /status → Confirm the file appears in "Setting sources" → If not: check for JSON typos or a higher-priority file overriding it

8The CI/CD gotcha: only ONE of these files actually reaches your pipeline

This is the part people get wrong most often. When your pipeline (GitHub Actions, GitLab CI, etc.) checks out your code fresh, it does not get your personal computer's settings.

FileReaches CI?Why
~/.claude/settings.json (user)✗ NoThis lives on YOUR computer's home folder — CI runners are fresh machines that have never seen it
.claude/settings.local.json (local)✗ NoDeliberately excluded from git (that's the whole point of "local") — so it never gets checked out
.claude/settings.json (shared project)✓ YesThis is the one you commit to git — so it's the only one that travels with the checked-out code
What this means for you: if you want Claude Code to have certain permissions (like "Agent" for subagents) when running in CI, you have exactly two choices: (1) commit them into the shared .claude/settings.json file, or (2) pass them as command-line flags in your pipeline config (e.g. --allowedTools "Agent" in GitHub Actions' claude_args). Anything sitting only in your personal user or local file will silently be missing in CI.

9Quick FAQ

Do I need to create all these files myself?

No. Claude Code creates ~/.claude/settings.json and .claude/settings.local.json for you automatically the first time you change a setting or approve a permission. You only manually create .claude/settings.json (the shared team one) if your project doesn't already have one.

Will my personal file accidentally get shared with my team?

No — Claude Code automatically adds .claude/settings.local.json to your global git-ignore the first time it writes to it, so it can never accidentally get committed.

What if I break a settings file with a typo?

Claude Code shows you a dialog at startup offering to fix it with Claude's help, or to just continue without that broken file. It won't silently fail on you.

Can my company force settings on me even if I disagree?

Yes — that's exactly what "Managed settings" is for. It sits at the very top of the precedence list specifically so a company's security policy can't be overridden by an individual developer.

I set something and it's not working. What's the very first thing to check?

Run /status inside Claude Code. It shows exactly which files loaded — nine times out of ten, the setting is either in the wrong file, or something higher up the precedence ladder is overriding it.
