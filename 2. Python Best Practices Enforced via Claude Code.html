Structuring Python Best Practices via Claude Code

Overview: To get the most reliable, production-ready Python code from Claude Code (or similar AI coding agents), you must structure its context logically. This relies on four pillars: Global Context (CLAUDE.md), System Guardrails (Hooks), Path-Scoped Guidelines (Rules), and On-Demand Workflows (Skills).

1. CLAUDE.md (Always-On Baseline Guidance)

The CLAUDE.md file sits at the root of your repository. It provides the foundational, non-negotiable context Claude needs to understand your project's ecosystem before writing a single line of code.

Main Best Practices to Enforce:

  • Toolchain Execution: Explicitly state CLI commands (e.g., uv add, pytest, ruff check) so Claude doesn't hallucinate package manager commands.
  • Core Language Standards: Mandate Python version (e.g., 3.12+), strict type hints (mypy strict mode), and docstring formats (Google/Sphinx).
  • Architecture & Layout: Explain the project structure (e.g., src/ layout, domain-driven design) so Claude places generated files in the correct directories.

Complete Example:

CLAUDE.md
# Python Project Guidelines

## Core Standards
- **Python Version:** 3.12+
- **Typing:** Strict typing is mandatory. All functions must have type hints for parameters and return types. Use `typing` module (or standard collections for Python 3.9+).
- **Docstrings:** Use Google-style docstrings for all public classes, methods, and modules.

## Toolchain & Commands
- **Package Manager:** We use `uv`. To install dependencies, run `uv pip install <package>`. Do NOT use `pip install` or `poetry`.
- **Formatting & Linting:** We use Ruff. 
  - Format: `uv run ruff format .`
  - Lint: `uv run ruff check . --fix`
- **Testing:** We use Pytest. Run tests via `uv run pytest tests/`.

## Architecture
- `src/api/`: FastAPI routers and endpoints only. No business logic.
- `src/services/`: Core business logic and use cases.
- `src/schemas/`: Pydantic v2 models for validation.
- `src/db/`: SQLAlchemy models and repository pattern classes.

Always prefer dependency injection over global state.

2. Hooks (Deterministic System Guardrails)

Hooks intercept AI agent actions at specific lifecycle events (e.g., before executing a command, after modifying a file, before concluding a task). They ensure formatting, linting, and testing are handled deterministically by the machine, not rely on the LLM's memory.

Main Best Practices to Enforce:

  • Post-Edit Formatting: Automatically run ruff format and ruff check --fix after the agent writes to a file.
  • Verification Gates (Stop Hook): Intercept task completion to run pytest. If tests fail, feed the error back to the agent instead of allowing it to stop.
  • Security Guardrails (Pre-Tool Use): Block the AI from accidentally modifying .env files, `.venv` folders, or historical database migrations.

Complete Example:

Note: This is represented as a shell script hook that a Claude agent wrapper might run after applying file changes (e.g., a post-edit script).

.claude/hooks/post_edit.sh
#!/bin/bash
# Hook triggered automatically after Claude writes/edits a Python file.

MODIFIED_FILE=$1

echo "Applying deterministic formatting and linting to $MODIFIED_FILE..."

# 1. Run Ruff Formatter
uv run ruff format "$MODIFIED_FILE"

# 2. Run Ruff Linter with auto-fix (imports, unused variables)
uv run ruff check --fix "$MODIFIED_FILE"

# 3. Run Type Checking
uv run mypy "$MODIFIED_FILE"
MYPY_EXIT_CODE=$?

if [ $MYPY_EXIT_CODE -ne 0 ]; then
    echo "HOOK BLOCKED: Mypy type checking failed."
    echo "Please ask Claude to fix the typing errors above before proceeding."
    exit 1
fi

echo "Hook completed successfully."
exit 0

3. Rules (`.claude/rules/*.md`)

Rules provide path-scoped context. Instead of cluttering the global CLAUDE.md with database-specific syntax, you define rules that only activate when Claude is working within a specific directory.

Main Best Practices to Enforce:

  • Data Validation (`src/schemas/`): Enforce Pydantic v2 standards, model_validator usage, and strict type coercion.
  • Async Execution (`src/services/`): Force the use of httpx for async requests, asyncio.TaskGroup, and ban blocking I/O calls.
  • Database Access (`src/db/`): Mandate SQLAlchemy 2.0 type-annotated declarative base mappings (Mapped[int]), and require explicit transactions.

Complete Example:

.claude/rules/database.md
---
description: "SQLAlchemy Database Models and Queries"
globs: ["src/db/**/*.py", "src/repositories/**/*.py"]
---

# Database Coding Rules

When working in `src/db/` or modifying database repositories, adhere strictly to **SQLAlchemy 2.0** standards.

## 1. Model Definitions
- Use strictly typed `Mapped[T]` and `mapped_column()` for all fields.
- Do NOT use the legacy `Column()` syntax.
- Use `String(255)` for bounded strings instead of generic `String`.

## 2. Queries and Execution
- Use `select()`, `insert()`, `update()`, and `delete()` constructs. Do not use legacy `Query` objects (`session.query()`).
- All database operations must use `AsyncSession`.
- Result fetching must use `await session.execute(stmt)`. Followed by `.scalars().all()` or `.scalar_one_or_none()`.

## Example
```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column
from src.db.base import Base

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    is_active: Mapped[bool] = mapped_column(default=True)
